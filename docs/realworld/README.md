### C. 영상 추적 (Colab T4, [tracking.json](tracking.json), [tracking_events.json](tracking_events.json), 시트: [tracking/](tracking/))

**SA-V 정답 대비** (240프레임 중 정답이 있는 60프레임, 클릭한 프레임에서 정방향 추적)

| 객체 | J (평균 / 최저) | F | **J&F** | 보이는지/가려졌는지 판정 |
|---|---|---|---|---|
| 객체 0 | 0.894 / 0.517 | 0.978 | **0.936** | 60/60 일치 |
| 객체 1 (아이) | 0.951 / 0.855 | 0.979 | **0.965** | 60/60 |
| 객체 2 (벽 그림, 가려짐 있음) | 0.862 / 0.545 | 0.977 | **0.919** | 60/60 (30~42프레임 가려짐을 정확히 "없음"으로 판정) |
| 객체 4 (조끼), **한 번 클릭** | 0.109 / 0.031 | 0.086 | ❌ **0.098** | 첫 프레임에서 아이 전신을 잡고 **끝까지 그대로 따라감** |
| 객체 4, **보정 클릭** (포함 1, 제외 2) | 0.911 / 0.816 | 0.998 | ✅ **0.954** | 60/60 |

- 첫 프레임 마스크가 맞으면 **모두 합격 기준(J&F 0.8 이상)을 통과**했습니다. 정확도는 추적보다 **첫 프레임 선택이 결정**합니다(객체 4: 0.098 → 0.954).
- **fp16 vs fp32** ([fp16_vs_fp32.json](fp16_vs_fp32.json)): J 차이는 최대 0.0006입니다. 같은 작업의 두 결과를 비교한 평균 IoU는 0.998~0.9999, 가장 낮은 프레임은 0.918(객체 2, 가려지는 순간)입니다. fp16이 **약 2.5배 빠르고**(프레임당 206ms vs 515ms) 메모리도 덜 씁니다(749MB vs 892MB). → **fp16 기본값을 유지합니다.**

| 내보내기 시간 (이 노트북 CPU) | 720p 10초: Color Pop 40~56초, Neon 122초, Blur 125~200초 (프레임당 163~670ms). 540p: 22~52초. 측정하는 동안 다른 분석 작업이 같이 돌아서 일부 값은 실제보다 클 수 있습니다 |

**프레임 누락 원인 (재현 확인)**: `app/exporter.py`의 FFmpeg 명령은 오디오를 붙일 때 `-t <추적 구간 길이>`와 함께 **`-shortest`** 를 씁니다. 같은 입력으로 FFmpeg를 직접 실행하면 `-shortest`가 있을 때 288프레임(9.6096초), **없을 때 289프레임(9.642967초)** 이 나옵니다. 오디오는 `-t`가 이미 길이를 맞추므로 두 경우 모두 9.642958초입니다.
→ 수정안: `-shortest`를 빼고, 오디오가 있는 영상으로 "출력 프레임 수 = 추적 프레임 수" 테스트를 추가합니다(아주 작은 작업). Phase 4 테스트는 이 조합을 잡아내지 못했습니다.

### E. 미리보기 렌더링 성능 (Chrome, 960×540, 이 노트북)

| 효과 | 중앙값 | 최대 가능 fps |
|---|---|---|
| 없음 (마스크 표시만) | 24ms | 41 |
| Neon / Color Pop / Blur 하나 | 30~32ms | 31~34 |
| **세 효과 모두** | **78ms** (p90 330ms) | **13** |

30fps 영상을 세 효과를 다 켜고 재생하면 **미리보기가 끊깁니다.** 내보낸 MP4는 프레임마다 렌더링하므로 영향이 없습니다.

### F. 동시 사용 (관찰된 문제)

검증 중 브라우저에서 CPU 추적(10프레임, 1분 44초)과 클릭 분할이 동시에 실행됐습니다. 이때 제 분할 요청은 2초 기다린 뒤 **`busy`(409)로 실패**했고, 추적 중에는 30초 넘게 계속 실패했습니다. 모델이 하나뿐이라 요청을 순서대로만 처리하는데, **대기열 없이 즉시 실패**하는 구조입니다.
